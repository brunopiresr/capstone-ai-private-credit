# In-app user guide implementation plan

Status: Implemented, 29 October 2026. The requirements below describe the delivered
guide and agent-generated questions. Live question quality and first-time-reader
usability remain human evaluation tasks; offline tests do not establish either.

## Goal and scope

Help a first-time analyst complete an assessment, understand its evidence, and
submit a validated report without leaving the app to read repository documentation.
Give returning users a quick way to look up a task or resolve a blocked action.

Target the connected Streamlit workspace launched with `make preview`
(`src/credit_monitoring/web/preview.py`). Its Portfolio and Borrower analysis
pages are connected, along with Documents & data, Risk review and Board report.
These workflows were connected after the initial plan was written; guide content
reflects the current saved operations rather than describing them as sample controls.

The original `make run` app has a different workflow and stays outside this first
release. Do not add a second assistant, a new backend, database tables, or an
interactive overlay tour. The guide itself requires no credentials or model calls.

## User experience

1. Add **User guide** as the last sidebar navigation item, available from every
   page. Keep Portfolio as the initial landing page.
2. Add a compact, dismissible **New here? Start with your first assessment**
   invitation on Portfolio. Dismissal lasts for the browser session; the sidebar
   entry always remains available. Opening the app must not force a tour.
3. Open the guide on **Get started**, followed by a topic selector for the task
   guides below. Use short numbered steps with the exact labels users see in the
   app, prerequisites, and an explanation of the expected result.
4. Provide **Open Portfolio**, **Open Borrower analysis**, and **Open Risk review**
   navigation buttons where relevant. These only navigate; they never assess,
   review, recalculate, validate, or submit on the user's behalf.
5. Add small, collapsed **How to…** help sections beside date/assessment controls,
   agent review controls, and validation/report forms. Reuse the corresponding
   guide content so users can read instructions without leaving unfinished work.
6. Offer **Back to previous page** from the full guide. Restore the selected
   borrower, dates, prediction mode, assessment version, and session-owned chat.
   Preserve expanded assistant state when returning from help. Treat form edits
   separately: explain **Save draft** before leaving a report; do not imply that
   unsubmitted forms are saved automatically.
7. Show up to three **Suggested follow-up questions** beside the borrower chat,
   generated by an agent from the selected saved assessment and its saved credit
   risk analysis.
   Selecting one fills an editable question draft; the user sends it explicitly
   through the same assistant.

Use the existing typography and native Streamlit controls. Keep the reading column
comfortable, explain data limitations with text rather than color alone, and check
keyboard navigation and narrow-screen readability. Use text instead of screenshots
for the first release so labels and instructions are easier to maintain.

## Content outline

| Topic | What the user should learn |
| --- | --- |
| Get started | Complete the core assessment-to-submission walkthrough below; understand which optional actions need model credentials. |
| Portfolio and dates | Search/select borrowers; choose a period and information cutoff; understand actual source periods; run one borrower or the whole catalog. Explain that **Assess all borrowers** includes borrowers hidden by filters. |
| Read an assessment | Find Overview and Calculations; interpret actual values, thresholds, headroom, verification and source references. Missing, conflicting, waived and inactive results remain distinct from compliance. |
| Credit reviews and forecasts | Request bullish, bearish and recommendation reviews on a saved version; provide criteria and assumptions; interpret Off, Stub and Logistic Regression. Explain the default bundled forecast and synthetic training limits. |
| Ask the assistant | Ask about saved evidence; use agent-generated follow-up questions; explain credentials, version-scoped conversation memory, expand/hide controls, and **Allow recalculation for this question**. |
| Validate, flag and submit | Complete the three checks; record exceptions; add flags; save a draft; submit to the saved Risk review inbox. Explain submission blockers and the read-only manager inbox. |
| Revisions and history | Recalculate with revised financial inputs and a reason; inspect Assessment versions and History; understand when new validation and reviews are needed. |
| Documents, manager and board workflows | Explain connected document operations, manager review, saved board reports, refresh/restart behavior and **Reset navigation**. |
| Troubleshooting and glossary | Resolve common blocked actions and define borrower, covenant, headroom, reporting period, cutoff, assessment, review, forecast and validation. |

### Core walkthrough

The main path should work without model credentials. Keep agent reviews and chat
as optional branches rather than prerequisites for submitting a report.

1. In **Portfolio**, choose a borrower and **Latest available per borrower**, or
   a reporting period available in the loaded data. Set the information cutoff
   on or after the period. Explain that bundled financials currently cover 2025;
   the loaded data determines connected period availability.
2. Leave **Include agent reviews** off and choose **Run selected assessment**.
   Expected result: a saved assessment appears, with its actual period and any
   data limitations. Opening or filtering the page alone does not run work.
3. Choose **Open borrower analysis**. Inspect **Overview** and **Calculations**,
   including source inputs, contractual terms, headroom and verification.
4. Optionally open **Credit analysis** and choose **Run agent review** after
   credentials are configured. The three agents review the selected saved version;
   assumptions entered as context do not become new evidence sources.
5. In **Report and review**, complete all three checks, record any exceptions,
   and choose **Mark validated**. Structured verification errors must be resolved;
   missing or conflicting data need explicit exception notes.
6. Add a flag when action is needed. A breach requires a flag for this assessment
   version or an explained breach triage decision. Write observations and a
   proposed recommendation, then **Save draft** or **Send to risk manager**.
7. Open **Risk review**, select the borrower and **Submitted version**. Explain
   that submission freezes its assessment/review, validation, flags and analyst
   text; manager comments, decisions and further-analysis requests are saved separately.

Use examples that follow the currently loaded catalog instead of hard-coding a
borrower count or promising a particular breach result. Include optional assistant
prompts such as “Explain the leverage calculation and its source inputs” and
“What evidence is missing from this assessment?”

### Agent-generated follow-up questions

Requirement: an agent generates the actual question text from the current
calculations and saved risk-agent outputs. Do not select questions from a fixed
library or substitute hardcoded questions when generation is unavailable. Any
questions shown in design discussions are illustrative, not implementation templates.

After the bullish, bearish and recommendation agents finish, run a focused
follow-up-question agent on their saved outputs and the exact assessment they
reviewed. Supply the financial inputs, calculation results, headroom, verification,
comparable trends, forecast metadata, and supporting evidence references. Also
supply the bullish and bearish arguments, counterevidence, argument judgments,
recommendation, confidence, conditions, gaps, uncertainties and diligence questions.

The agent should generate up to three concise, distinct questions that would help
an analyst understand or challenge this particular analysis. It chooses the topics,
wording and priority from the supplied findings. The prompt should encourage
specific questions about consequential calculations, tensions between perspectives,
recommendation assumptions and evidence gaps. It must not force a generic question
for each role or invent disagreement, missing facts or unsupported conclusions.

Generation and display:

- Treat follow-up generation as an additional model call within the explicit risk
  review workflow, with progress and provider usage reflected in that action.
  For batch reviews, generate once per newly reviewed assessment after its review
  finishes, rather than after each individual agent stage.
- Return structured suggestions containing question text, a short explanation of
  relevance, assessment/review IDs, and references to the supporting calculation,
  argument, judgment or review field. An assumption or agent interpretation must
  remain distinct from a verified financial fact.
- Give the generation agent read-only context and no execution tools. It must not
  recalculate, fetch documents, run the risk agents again, change validation, or
  modify analyst decisions. Requests for hypothetical analysis must stay within
  the capabilities exposed by the current chat.
- Validate scope, reference existence, nonempty text, bounded lengths, duplication
  and the three-question limit. Reject invalid suggestions rather than replacing
  them with hardcoded questions. Do not require exact wording or deterministic
  output from the agent.
- Save generated suggestions separately from immutable assessment/review snapshots
  in local runtime storage, keyed by assessment ID, review ID, input-context hash,
  model and prompt version. Reuse them on navigation and browser reruns. No new
  database tables are needed; use a small versioned sidecar record with atomic
  writes. Never serve suggestions from another analysis or input context.
- For existing saved analyses without suggestions, offer **Generate follow-up
  questions**. Offer **Regenerate questions** for an explicit retry or new set;
  opening the page or guide alone must not trigger generation.
- Without a saved credit review, an explicit **Generate follow-up questions** action
  may use calculations alone, clearly identifying the available context. Once a
  matching review is saved, generate from the combined calculations and risk
  analyses and retire the older calculation-only suggestions.
- With incomplete or blocked reviews, supply available outputs and explicit stage
  failures so questions reflect limitations without implying every agent completed.
  Generation failure preserves the assessment and review; allow retry and free-text
  chat. Without credentials, show previously saved suggestions if available, or
  explain that generation needs credentials. Do not display a template fallback.

Place suggestions above the question box in both the assistant panel and expanded
assistant. Display the agent's short explanation of relevance. Selecting a question
fills an editable draft and does not send it or make another model call. Preserve
one draft across panel/expanded views, and never overwrite a nonempty user draft.
The user sends the question explicitly; the existing recalculation checkbox remains
user controlled and off unless the user enables it.

Refresh the displayed suggestions when the selected borrower, assessment version or
saved review changes. Clear stale suggested drafts and check the bound IDs again
before sending. Reuse matching saved suggestions or show the explicit generation
action; do not generate merely because navigation changed the selection.

The current assistant receives assessment tools but not the saved credit review.
Extend its per-turn context to include the exact matching review, arguments and
judgments, recommendation, conditions, confidence, uncertainties and diligence
questions, together with supporting snapshot evidence. Keep review findings,
deterministic facts and the user's question separate. This lets the assistant
answer questions about the saved risk analysis without reconstructing or rerunning
the three risk agents. Retain conversation history while explicitly identifying
the current review when a new review is selected or saved.

Use notebook 03's relevant questions as evaluation scenarios, not a canned question
bank. Filing research and arbitrary cross-period calculation prompts need tools the
current chat does not expose; instruct the generation agent to avoid those requests.
A connected Document research chat remains a separate capability proposal.

### Troubleshooting entries

- **No assessment or missing financials:** check the selected borrower, actual
  period and cutoff; explain that the app does not substitute a different quarter.
- **Agent review or assistant unavailable:** ask the app operator to configure
  `OPENAI_API_KEY`; calculation-only work remains available. Never ask users to
  paste secrets into chat. Agent actions incur provider usage.
- **Forecast unavailable:** explain the selected mode, required ML dependencies
  and model artifact; distinguish Stub from the trained model. For a saved ML-off
  assessment, explain **Run assessment with ML** and then a new review.
- **Validation or submission blocked:** explain unchecked validation items,
  verification errors, missing exception notes, empty report text, and missing
  breach flags/triage; point to the relevant existing control.
- **Validation needed again:** new assessments, recalculation and new credit
  reviews need fresh validation. Earlier submissions remain frozen.
- **Changes after refresh or reset:** saved assessments, flags, reports and generated
  questions survive; browser-owned conversation memory has a different lifetime.

## Implementation steps

1. **Write the content.** Adapt the existing
   [POC walkthrough](../guides/ui_preview.md) and verify every instruction against
   `portfolio.py`, `borrower_analysis.py` and `preview.py`. Keep user instructions
   free of internal storage paths; retain operational details in the docs.
2. **Add a small guide module.** Create
   `src/credit_monitoring/web/user_guide.py` with topic IDs, reusable topic text,
   a guide page renderer and a contextual-help renderer. Keep guide rendering
   independent of application services and avoid a generic content framework.
   The module is the shared source for full-page and inline help copy.
3. **Wire navigation.** Update `PAGES`, `render_sidebar()` and the route mapping
   in `preview.py`. Give User guide its own neutral help header. Add invitation and
   return-navigation state with dedicated `guide_` keys. Reuse the existing
   pending-page navigation mechanism; do not mutate a rendered navigation widget.
4. **Preserve working context.** Use non-widget session state to retain relevant
   selections while their widgets are absent. Handle the existing `main()` branch
   that collapses chat on every page other than Borrower analysis, so visiting the
   guide can restore the assistant's previous expanded state. Do not close or
   recreate its conversation. Use inline help for unfinished forms.
5. **Place contextual help.** Add the Portfolio invitation and date/run help in
   `portfolio.py`, shared agent help in `render_review_controls()`, and assistant,
   revision and handoff help in `borrower_analysis.py`. Add operation help in the
   document, risk-review and board-report renderers. Keep help collapsed by
   default so the working screens retain their space.
6. **Add agent-generated follow-ups.** Create a focused agent in
   `agents/follow_up_questions.py` with a typed output contract and a service in
   `application/follow_up_question_service.py` to assemble bounded assessment/review
   context, validate references, execute generation and manage saved suggestions.
   Invoke it after explicit review completion, and expose generation/retry for older
   runs. Render suggestions in `render_chat()` with an editable draft and explicit
   Send. Keep generation independent of answering or recalculating an assessment.
7. **Supply saved risk analysis to chat.** Extend the existing question-context
   assembly used by `render_chat()` and `ask_about_assessment()` to accept the
   matched saved review and its evidence. Bound its size, retain source references
   and distinguish interpretation from source facts. Validate identity on every
   turn and handle new reviews on the same assessment without silently reusing old
   review context. Keep existing callers without review context working.
8. **Verify and document.** Add focused integration coverage and update
   `docs/guides/ui_preview.md` and the root README to mention the in-app entry
   point. Reconcile duplicated workflow instructions whenever controls change.

## Validation and acceptance

Add `tests/integration/workflows/test_streamlit_user_guide.py`, using the existing
Streamlit AppTest patterns, temporary storage and controlled services. Cover:

- Opening every topic without credentials, assessment calls, agent calls,
  document processing, network requests or guide-triggered persistence writes.
- Reachability from every page, correct guide labeling, invitation dismissal,
  and navigation buttons that only change pages.
- Round trips preserving borrower, dates, prediction mode, saved assessment
  selection, chat messages and the same conversation object. Check narrow widget
  lifecycle cases explicitly rather than assuming session state retains widgets.
- Inline help near forms retaining in-progress edits; opening help must not
  submit a form or mark an assessment validated.
- Unchanged saved assessment, review, validation and submission records after
  browsing help, including the navigation-reset interaction with guide session state.

Add focused generation tests in `tests/unit/agents/test_follow_up_questions.py`,
service tests with temporary storage, and chat interaction cases in the existing
borrower-analysis integration tests. Use controlled model responses to cover:

- The generator receives the exact calculation results plus bullish, bearish and
  recommendation outputs, including gaps, confidence and supporting evidence.
  Changes to either calculations or review findings change the supplied context
  and invalidate previously saved suggestions.
- Structured-output validation, valid finding references, scope enforcement,
  deduplication and the three-question limit. Malformed output, missing credentials
  and provider failures preserve analysis and never introduce hardcoded fallbacks.
- One generation call after a new review completes, including batch review paths.
  Navigation, guide browsing, selection and panel expansion reuse saved suggestions
  without generation calls. Explicit regeneration makes one fresh call.
- Correct behavior for calculation-only, missing, incomplete, blocked and mismatched
  reviews, and for a new review saved on the same assessment.
- Suggestions carry their actual analysis scope, preserve a nonempty draft and
  share the same draft between panel and expanded views. Clicking a suggestion
  makes no model calls or writes; sending produces one user turn through the
  existing conversation and never enables recalculation automatically.
- Follow-up answers receive the matching risk analysis and evidence references;
  neither generation nor answering reruns the three review agents.

Use an opt-in quality evaluation with varied saved analyses to judge whether the
questions identify specific findings, useful tensions or uncertainties and can be
answered with the available evidence. Include pairs with identical calculations
but different risk-agent conclusions. Score relevance, grounding and usefulness;
exact wording is not an acceptance criterion. This evaluation makes provider calls
only when explicitly invoked; routine automated tests remain offline.

Run the new tests plus the existing preview and borrower-analysis integration
tests, then Ruff on changed Python files. Fix regressions and broaden checks when
failures indicate shared behavior has changed. No live provider calls are needed.

Manually walk through the core path without credentials, inspect optional-agent
instructions with credentials unavailable, and check keyboard/narrow-screen use.
Have a first-time reader attempt an assessment-to-submission task using the guide;
use any hesitation or misleading instruction to revise the copy.

Accept the feature when a new user can find the guide, save and inspect an
assessment, understand any blocking issue, submit a valid report, and locate it
in the saved inbox. They must also be able to distinguish synthetic inputs from
real service operations and return from help without losing their saved working context.
Suggested follow-ups must be generated by an agent from both the selected saved
assessment and the matching credit risk analysis, and allow the user to edit and send a relevant
question without triggering work merely by selecting it. The assistant must receive
the saved analysis and evidence needed to answer review-derived questions.
